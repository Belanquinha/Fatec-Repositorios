# Spine Pair Review — Fatec-Repositorios

Round: 2026-09-29 update (institution picker) over the 2026-09-23 spines (Home + Perfil hub).
Sources read: `SPEC.md`, `prd.md`, `epics.md`, `DESIGN-STORY-3.1-UPLOAD-PROJETO.md`, `planning-artifacts/.memlog.md` (entries 14–34), `sprint-change-proposal-2026-09-23.md`, `ARCHITECTURE-SPINE.md` (AD-1..AD-9), `sprint-status.yaml`, plus the five shape references and `references/design-md-spec.md`.

## Overall verdict

The round's own deliverable — one shared combobox in three modes — is the best-specified thing in either spine: the ARIA 1.2 keyboard map, the honest dead-end, the three-mode divergence rule and the recorded contract contradiction are all committed, and DECISAO 1–11 are implemented faithfully (including DECISAO 10's retargeting of the hero CTA and the header menu). But the pair is not yet a safe contract: the a11y gate asserts WCAG AA coverage it does not have, and **every token this round introduced sits outside that assertion** — including two that fail it; the palette has **no error token at all** for four required error states while forbidding the only red it owns; a whole journey (UJ-3 / admin catalog, whose story is `in-progress` right now) has no flow, no behavioural rule and no visual spec; and two contract conflicts are mis-recorded — one already closed in 2026-09-23, one silently invalidated in `epics.md` Story 2.2. A consumer can build the institution picker from these spines; they cannot build the admin catalog, cannot verify contrast, and would mis-patch the PRD.

## 2. Token completeness — broken

Checked: all 22 `colors` entries (every one carries a hex — no missing-hex defects), 9 `typography` roles, 5 `rounded`, 15 `spacing`, 3 `elevation`, 17 `components` blocks, and every `{path.to.token}` reference in both spines' prose and component objects. Existence is clean (matches the stated mechanical check). What fails is **type correctness at the a11y gate** and **contrast coverage for the new tokens**.

### Findings
- **[critical]** **The palette defines no error colour, yet four required error states exist and the only red is forbidden for them.** `colors` (DESIGN.md:6–30) has `cps` `#B20000` and nothing else in the danger family — no `error`, `danger`, `destructive`, no error surface/background. But the product must render errors at: the rejection dialog's server error ("erro do servidor exibido no dialog, sem vermelho CPS", EXPERIENCE.md:101), the professor route's Save failure, the Home/Perfil API-error panel ("Sem vermelho CPS", EXPERIENCE.md:121), and the blocked submit (finding 1.2). DESIGN.md:296 **bans** red for errors ("Reservar o vermelho CPS para marca/institucional | Vermelho em erro, alerta ou badge de rejeição"). Net effect: a consumer must invent the error colour, and the obvious invention violates a Don't. The one place this is arguably solved is `status-rejected` (neutral `#202124` on `#E9E9E9`, 13.3:1) — but "the project was rejected" is a domain state, not a system error, and the spine never says the same treatment governs errors. *Fix:* add `error: '#1A1A1A'`-class token (or a `danger-neutral` pair) plus a written rule that system errors are neutral ink on `{colors.surface}` with `{colors.border}` emphasis, explicitly *not* `cps`; and add an `input-error` border token so the blocked submit has a border treatment that is not red.
- **[critical]** **`status-pending` (`#9C7702`) fails AA text contrast on every surface in the system, and it is load-bearing in two places — one of them new this round.** Computed: `#9C7702` on `status-pending-bg` `#FCF6E6` = **3.85:1**; on `surface` `#FEFEFE` = **4.09:1**; on `background` `#F4F6F9` = **3.84:1**. All below the 4.5:1 the spine itself claims (EXPERIENCE.md:156). It colours (a) the "Aguardando aprovação" badge text (DESIGN.md:25, 180) and (b) **the new at-cap selection-counter** — `at-cap-foreground` (DESIGN.md:173), the climax of DECISAO 6 and Flow 3 step 7 ("4 de 4 unidades"), the exact state the round built the counter to communicate. *Fix:* darken `status-pending` to `#7A5C02`-range (≥4.5:1 on `#FCF6E6` requires roughly L ≤ 0.175; `#8A6802` lands ≈4.6:1) and re-verify, or introduce `status-pending-ink` distinct from the badge fill. This cannot be waved through as inherited: the *pair* on the new component is new even though one member is old.
- **[critical]** **The 2px `{colors.primary}` focus ring and the new `combo-option` check mark sit at 2.0–2.2:1, and the spine asserts they are legible.** `{colors.primary}` `#DCA703` on `{colors.surface}` `#FEFEFE` = **2.18:1**; on `{colors.primary-soft}` `#FCF6E6` = **2.03:1**. WCAG 1.4.11 requires 3:1 for the visual information identifying a UI **state**, which a focus ring and a selected-state mark both are. EXPERIENCE.md:170 states outright that the ring is *"legível sobre `{colors.surface}` e sobre a opção ativa em `{colors.primary-soft}`"* — that claim is numerically false on both surfaces named, and `{components.combo-option.selected-mark}` (DESIGN.md:157) is the same failing pair. In `multi`, that check is the only visual mark that an option is already committed. *Fix:* either give the field a `focus-ring` token using `text`/`text-strong` with the yellow reserved for the 2px inset (the combobox already uses a yellow left-inset for the active row — reuse that vocabulary), or state a measured 3:1 pair for both surfaces and re-verify; and add `aria-selected` + a non-colour differentiator for `combo-option` beyond the glyph.
- **[high]** **The AA audit is misdirected, mis-scoped, and misses every new pair.** Three problems in one sentence (EXPERIENCE.md:156): (a) it defers contrast to `DESIGN.md` — *"Contraste visual vive em `DESIGN.md`"* — and **DESIGN.md contains no contrast section, no ratios and no targets anywhere**; the pointer resolves to nothing. (b) It verifies *"verde `#00B32A` × `#004B12`"* — **`#004B12` is not a token in DESIGN.md** (the whole palette is 22 tokens; this hex appears nowhere else in either spine), and the pair computes **3.71:1**, below its own stated 4.5:1. (c) The green pair that actually ships — `status-approved` `#007F1E` on `status-approved-bg` `#E6F7EA` = **4.65:1**, passing by 0.15 — is **unverified**, and so is every pair this round added: `status-pending`/`status-pending-bg` (fails), `primary`/`surface` for the ring and the check (fails), `primary`/`primary-soft` for the active option row (fails), and `institution-chip`'s `border-soft` `#98999A` on `surface`/`background` = **2.83:1 / 2.64:1** (fails the 3:1 boundary test). The claim *"todos ≥ 4.5:1 nos usos previstos"* is inherited by assertion and is false as written. *Fix:* put the audit **in DESIGN.md** (a `## Contrast` block or a `contrast:` frontmatter map of `foreground/background → ratio`), list every load-bearing pair including the four above, and delete the `#004B12` reference or add it as a real token.
- **[low]** **Frontmatter type deviations from `design-md-spec.md`.** `typography.label.textTransform` (DESIGN.md:86) is outside the spec's typography subset (`fontFamily`/`fontSize`/`fontWeight`/`lineHeight`/`letterSpacing`) — a strict flattener drops it, and the uppercase label treatment then exists only in prose (Typography, line 239). Four component tokens embed `{…}` inside larger CSS strings rather than using pure refs (`button-secondary.border`, `institution-autocomplete.focus-border`, `combo-option.active-inset`, `combo-option.title`), so a strict resolver yields non-CSS literals. `elevation` is a non-spec top-level block that both spines depend on. *Fix:* move `textTransform` to prose or wrap it in a `note:`; keep compound CSS but declare the resolver tolerance; declare `elevation` in the frontmatter comment as a project extension.
- **[low]** **`combo-option.title` declares a font but no colour** (DESIGN.md:153) — family/size/weight only, while `meta` correctly declares `{colors.text-muted}`. The option title is the row's primary text and the one element the missing contrast audit should cover. (Low severity: every plausible default — `text` 15.96:1, `text-strong` — passes, so nothing downstream breaks.) *Fix:* add `foreground: '{colors.text}'`.

## 3. Component coverage — adequate

Checked: every component name appearing in either spine against DESIGN.md.Components (270–288) *and* EXPERIENCE.md.Component Patterns (87–102), requiring real rules rather than one-word descriptions. **The `combo-popup` / `combo-option` split is defensible, not a coverage hole.** All their behaviour is carried by the parent row — open only on non-empty query, the four match fields with accent-insensitive normalisation, Enter/click confirm, focus never leaving the input, `Tab` commit-and-exit — plus the full ARIA 1.2 keyboard map (139–150) and the Accessibility Floor's `role="listbox"` / `role="option"` / `aria-selected` rows (159). Adding separate rows would duplicate the parent and create a second place for the keyboard contract to drift. The misses below are elsewhere.

### Findings
- **[high]** **The approval / rejection dialog has behaviour but no visual contract.** EXPERIENCE.md:101 specifies a dialog with a mandatory `textarea` for `motivoRejeicao` and an inline server error — and DESIGN.md has **no dialog component, no modal surface token, no overlay/scrim token, no textarea/field-error style, and no focus-trap or dismiss rule** anywhere. A consumer building it has to invent the entire visual treatment. *Fix:* add a `dialog` component token (surface, border, `elevation.raised`, scrim colour + opacity) and a DESIGN.md Components bullet; add the missing focus-containment/`Esc`-dismisses-with-unsaved-motive rule to Interaction Primitives (note the existing ban on "modais em pilha").
- **[medium]** **`filter-chip` is named as a component but exists in only one place.** DESIGN.md:277 co-names it in the `filter-select` bullet ("`filter-chip` permanece para os chips de palavras-chave; chip ativo em `{colors.primary}` com texto `{colors.primary-foreground}`") — but there is **no `components.filter-chip` token**, and EXPERIENCE.md gives it behaviour only as a subordinate clause inside the generic "Filtros" row ("Mais os chips de palavras-chave, combináveis"). A consumer grepping `filter-chip` finds no token path and no behavioural row. *Fix:* promote it — its own token block and its own Component Patterns row (add/remove, combinable with the institution filter, active-state distinction).
- **[medium]** **`profile-name` is a declared component token with no spec anywhere** (DESIGN.md:200–203): no Components bullet of its own, no Component Patterns row. Its rules are buried inside `profile-header` ("nome (`h2`)"). *Fix:* fold the three tokens into `profile-header` or give `profile-name` a bullet + row so the frontmatter doesn't advertise a component no consumer will find.
- **[medium]** **The "Professor Convidado" badge has no visual or behavioural spec.** It is required by CAP-4/AD-6/FR-9/Story 3.2, and DESIGN-STORY-3.1 §2 (a `sources:` document) fixes its exact copy (`[ ✉️ Professor Convidado — registro informativo, sem envio de notificações ]`). In the spines it appears only as two passing mentions (EXPERIENCE.md:81 and :184) — no token, no Components bullet, no Component Patterns row. The email typeahead itself is explicitly deferred as a known deficiency (EXPERIENCE.md:152), but the badge is the informative artefact FR-9 depends on and Story 3.2 is `backlog`. *Fix:* add a `badge-informative` token (`corporate-soft` on `corporate`, per the "dicas informativas" semantic at DESIGN.md:228) + Components bullet + Component Patterns row ("appears only when the typed e-mail is not in the tenant list; informative, no notification"), or state in the deferral note that the badge ships with the deferred typeahead and name the owner.
- **[low]** **The sticky submit footer is a real element with no spec.** `elevation.sticky-footer` exists (DESIGN.md:211), a hard responsive rule depends on it ("o rodapé sticky de submit **nunca** fica coberto pelo popup", EXPERIENCE.md:178), and DESIGN-STORY-3.1 §4 ships the exact HTML — yet there is no token block, no Components bullet (Elevation hedges it with "se houver", line 260), and no Component Patterns row. *Fix:* add a `sticky-footer` component token and one behavioural rule (always visible; never covered by the popup's z-index; disabled state during submit).

Checked: every IA surface (EXPERIENCE.md:44–53) against empty / cold-load / focus / error / offline / permission-denied, plus the six combobox-specific states. **The round's own combobox states are the strongest part of the file:** empty-query (109), no-match (110), not-in-catalogue (111), committed (112), cap-reached (113), dirty (114), catalog-loading skeleton (108), anonymous/ALUNO redirect (115), offline (124) — all present with committed treatments. - **[medium]** **The `single`-mode committed-value lifecycle has three undefined transitions, all introduced this round.** (a) **Deep-link pre-fill:** `?instituicaoId=` pre-fills the combobox (EXPERIENCE.md:126) but nothing says whether a pre-filled value is already `committed` (meta row + "Alterar" shown?) or must be confirmed, nor whether it satisfies `instituicaoId` on submit — this directly affects FR-9 persistence. (b) **"Alterar" then cancel:** the keyboard map defines Esc as "fecha o popup **mantendo** a consulta; um segundo `Esc` limpa a consulta" (146) — with an empty query the second Esc clears nothing, so what happens to the previously committed unit is unstated. Undefined, and it interacts with `aria-required`. *Fix:* three explicit rows in State Patterns: "Pré-preenchido por deep-link", "Alterar cancelado", "Enter sem consulta".
- **[medium]** **No result-set rule for a type-to-reveal over 86 rows.** The Accessibility Floor announces an exact count ("12 unidades para 'ipir'", EXPERIENCE.md:160), but there is no **maximum result count**, no **sort order**, and no `scrollIntoView` rule for the `aria-activedescendant` active option (which the pattern requires — without it, keyboard navigation runs off-screen). Type "f" and every implementation differs. Also inconsistent scoping: "Unidade fora do catálogo" is scoped to the student's Section 2 in State Patterns (111) but to "Formulário do aluno · rota do professor" in Component Patterns (94) — the professor route's dead-end has a treatment in one table and not the other. *Fix:* add a cap (e.g. first 20 + "refine a busca"), a sort (nome, then cidade), the scroll-into-view rule, and align the two scopes.
- **[medium]** **Three-way internal contradiction on the empty-query open rule — the flagship component's most-implemented behaviour.** State Patterns: *"**Nenhum popup.** O campo é um input vazio"* (109). Keyboard map: *"Abre **apenas se houver consulta**; com o campo vazio nada abre"* (141). Accessibility Floor: *"O popup nunca é hover-only: abre por foco, clique ou teclado em qualquer viewport"* (163). Two sources say focus does not open it; the third reads as saying it does. *Fix:* rewrite 163 as "abre por **clique ou teclado** (nunca por hover), e apenas quando há consulta".
